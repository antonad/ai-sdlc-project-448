# Симулятор политик доступа

Учебный проект Хекслета (ai-sdlc). Браузерное приложение: React 19 + Mantine + TypeScript, сборка Vite, тесты Vitest. Серверной части нет.

## Как разложен код

- `src/domain`: модель данных (`model.ts`) и расчёт доступа (`access.ts`), чистые функции без браузера и часов.
- `src/app`: хранилище браузера, формат файла конфигурации, операции над разрешениями и хук `useSimulator`; реэкспортирует типы из `domain`.
- `src/components`: экраны на React и Mantine, берут всё из `../app` и передают в него действия человека.
- Тесты лежат рядом с кодом (`*.test.ts`, `*.test.tsx`). Подробности и правила импортов: `docs/architecture.md`.

## Команды

| Что | Команда |
| --- | --- |
| Установка | `npm ci` |
| Dev-сервер (порт 8080) | `npm run dev` |
| Тесты | `npm test` |
| Типы | `npm run typecheck` |
| Линтер и формат | `npm run lint` (исправить: `npm run lint:fix`) |
| Архитектурные правила | `npm run lint:arch` |
| Сборка | `npm run build` |

Те же проверки доступны через make: `make test`, `make lint`, `make lint-arch` (их запускает CI), `make setup`, `make dev`.

Перед завершением любой задачи пройти по порядку: `npm run typecheck`, `npm test`, `npm run lint`, `npm run lint:arch`, `npm run build` (тот же список у скила `verify`). Если менялась логика, дополнительно `npm run test:coverage`: пороги покрытия заданы в `vite.config.ts`.

CI (`.github/workflows/ci.yml`) запускает `make setup` (`npm ci` и `npm run build`, куда входит проверка типов), затем `make test`, `make lint`, `make lint-arch`. Покрытие CI не проверяет, поэтому пороги держатся только локальным запуском `npm run test:coverage`.

## Жёсткие правила

- Расчёт доступа только в `src/domain/access.ts`. Часы не читать, момент приходит параметром `at`.
- Компоненты берут всё из `../app`, включая типы. Не импортировать `src/domain`, не трогать `localStorage`.
- Никаких `fetch`, `XMLHttpRequest`, `WebSocket`, `sendBeacon` в `src`.
- Импорт файла проверяется целиком до изменения данных. Операции меняют только выбранные разрешения.
- Новая логика сопровождается тестом рядом с кодом (`*.test.ts`, `*.test.tsx`).
- Реализацию ведёт скилл `tdd`: зови его при новой логике и при исправлении. При первом запуске он спросит, на каких границах модуля писать тесты; на вопрос нужно ответить.
- Не редактировать, не удалять и не переименовывать `.github/workflows/hexlet-check.yml`.
- Новое архитектурное правило оформляется файлом в `rules/*.yml` (ast-grep) и проверяется `npm run lint:arch`.

## Стиль

- Формат и линт: oxfmt и oxlint, конфиг по умолчанию. Окончания строк LF (`.gitattributes`).
- Тексты интерфейса, сообщения об ошибках и комментарии на русском.
- Файлы правит Edit или Write. `Get-Content`/`Set-Content` портят кириллицу и добавляют BOM; `npm run lint` это ловит (`scripts/check-encoding.mjs`).
- Работа по спецификации: сначала тест или критерий приёмки, затем код, затем проверки выше.

## Процесс изменений (OpenSpec)

Спецификации лежат в `openspec/specs/` (четыре возможности: расчёт доступа, управление разрешениями, обмен конфигурацией, хранение) и описывают текущее поведение. Любая доработка идёт как изменение OpenSpec:

1. Требования: `/openspec-explore`, затем `/openspec-propose "<идея>"`. Решения записываются в `openspec/changes/<имя>/`.
2. Дизайн: решить, в каком слое живёт логика (см. `docs/architecture.md`).
3. Реализация: `/openspec-apply-change`, код вместе с тестами по задачам.
4. Независимое ревью: отдельная сессия, скил `review-diff`, сверка с изменением и документами в `docs/`.
5. Проверки: скил `verify`, результат читает человек.
6. Выпуск: `/openspec-archive-change` после влития, Pages публикует новую версию.

Код не пишется без изменения OpenSpec, кроме мелких правок без смены поведения. Проверка спек: `npx @fission-ai/openspec validate --specs`.
