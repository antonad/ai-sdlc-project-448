# Design

## Context

Причина: `importJson` в `src/app/index.ts` кладёт `result.config` как есть. Отзыв хранится только в `revokedAt` разрешения, а файл, выгруженный до отзыва, этого поля не содержит.

Ограничения: расчёт доступа только в `src/domain/access.ts`; компоненты берут всё из `../app`; файл проверяется целиком до изменений (СБ 2); операции меняют только затронутые разрешения (СБ 3).

## Decisions

### Перенос в слое приложения после проверки

`carryOverRevocations(current, imported)` в `src/app/permissions.ts` — чистая функция. `importJson` вызывает её только когда `parseConfigFile` вернул `ok`, поэтому отказ по-прежнему ничего не меняет. Формат файла и домен не трогаются, версия остаётся 4.

### Что считается тем же разрешением

Полное совпадение `id`, субъекта (тип и id), `serviceId`, `startsAt` и `expiresAt`. Совпадения одного `id` недостаточно: `nextPermissionId` переиспользует номера, и под тем же `p5` в файле может лежать другое разрешение. Если интервал в файле иной, отзыв не переносится: это уже другая выдача.

### Какой момент берётся

Нет `revokedAt` в файле: берётся из текущей конфигурации. Есть в обоих: более ранний (строка UTC сравнима лексикографически). Оба момента строго внутри одного и того же интервала, значит результат проходит проверку файла и круговой обмен.

### Альтернативы

- Сливать конфигурации целиком: ломает «импорт заменяет конфигурацию» (удалённое в файле должно исчезнуть).
- Предупреждать, не меняя: человек всё равно получает открытый доступ, пока не прочитает.

## Risks / Trade-offs

- Отзыв нельзя «отменить» импортом старого файла; отмены отзыва нет и в интерфейсе. Снять отзыв можно, удалив разрешение и выдав заново.
- Разрешение, удалённое кнопкой, а потом возвращённое старым файлом, вернётся без отзыва: следов удаления в данных нет. Вне рамок.
