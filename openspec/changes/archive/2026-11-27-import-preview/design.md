# Design

## Context

`importJson` проверял файл и сразу заменял конфигурацию. Нужен промежуточный шаг, на котором человек видит последствия. Ограничения: расчёт доступа только в `src/domain/access.ts`; компоненты берут всё из `../app`; файл проверяется целиком до изменений (СБ 2); данные остаются в браузере (СБ 1).

## Decisions

### Где живёт логика

- Слой `src/app`: чистая функция `buildImportPreview(current, imported)` в `import-preview.ts`. Хук держит в памяти один проверенный, но не применённый файл (`pending`) и отдаёт `importPreview`, `confirmImport`, `cancelImport`. Компонент только рисует строки и передаёт нажатия.
- Домен не тронут: в предпросмотре нет расчёта доступа, только сравнение записей.

### Что сравнивается

Предпросмотр сравнивает текущую конфигурацию с `carryOverRevocations(current, imported)`, то есть с тем, что подтверждение действительно сохранит. Иначе при файле, снятом до отзыва, предпросмотр показал бы «изменится: отзыв пропадёт», а подтверждение отзыв оставило бы.

Виды строк (по `id` разрешения):

- `added`: id есть в результате и нет в текущей конфигурации.
- `removed`: id есть в текущей конфигурации и нет в результате.
- `changed`: id есть в обоих, содержимое (субъект, сервис, `startsAt`, `expiresAt`, `revokedAt`) различается. Такое разрешение не называется ни выданным, ни убранным.
- `kept`: у текущего разрешения есть отзыв, итог равен текущему, а файл отзыва не содержит или содержит другой момент (более поздний). Это не различие: итог совпадает с текущим, поэтому строка не `removed` и не `changed`. Более ранний отзыв из файла даёт `changed`, потому что момент меняется.

Строки разрешений совпадают с различиями до и после подтверждения: других строк о разрешениях нет, `kept` строкой различия не является.

### Пустой предпросмотр

`import-preview-empty` показывается, когда нет ни строк разрешений, ни `kept`, ни различий пользователей, групп и сервисов. Файл, равный текущей конфигурации, даёт именно такой результат.

### Пользователи, группы, сервисы

Решение: показывать сводкой чисел в одном элементе `import-entities` (`добавлено N, убрано N, изменено N`), без отдельных строк. Подробные строки по ним вне задачи, но молчать нельзя: подтверждение заменяет и эти списки, а «ничего не изменится» при другом списке пользователей было бы ложью. Идентификатор не начинается с `import-preview-`, чтобы не смешиваться со строками разрешений.

### Предпросмотр считается заново, а не запоминается

В состоянии хранится проверенная конфигурация из файла, а различия считаются при каждом показе от текущей конфигурации. Если при открытом предпросмотре человек отзовёт разрешение, строки обновятся, а подтверждение применит файл к актуальной конфигурации и отзыв сохранится. Запомненная «фотография» различий разошлась бы с тем, что подтверждение сохранит.

### Предпросмотр не переживает перезагрузку и ничего не пишет

`pending` лежит только в состоянии React: в `localStorage` ничего не пишется до подтверждения, после перезагрузки предпросмотра нет. Файл с ошибкой сбрасывает `pending`; новый корректный файл заменяет прежний.

### Правило отзывов (изменение требований по инциденту с импортом)

Прежнее решение (`keep-revocations-on-import`) уже допускает только такое поведение: отзыв после экспорта остаётся в силе после загрузки файла, снятого до отзыва, потому что `carryOverRevocations` переносит `revokedAt` на то же разрешение (полное совпадение `id`, субъекта, сервиса, `startsAt`, `expiresAt`). Восстановления доступа после подтверждения решение не допускает, поэтому правило не ослабляется и не меняется. Меняется только момент применения: перенос выполняется при `import-confirm`, а не при выборе файла. Дополнительно закреплено, что отзыв, сделанный при открытом предпросмотре, тоже сохраняется. Сквозной тест: `ImportPreview.test.tsx`, «отзыв после экспорта остаётся в силе после подтверждения».

### Статус импорта

`import-status` показывается только после `import-confirm` и пропадает при выборе следующего файла. Остальные требования, где сказано «`import-status` сообщает «Конфигурация заменена»» после загрузки, теперь относятся к моменту после подтверждения.

### Альтернативы

- Сравнивать с «сырым» файлом: предпросмотр лгал бы про отзывы.
- Хранить `pending` в `sessionStorage`: нарушает «после перезагрузки предпросмотра нет» и добавляет работу с хранилищем в предпросмотр.
- Применять и давать «Отменить» после: нарушает «отмена ничего не меняет», в `localStorage` остался бы след.

## Risks / Trade-offs

- Различия пользователей, групп и сервисов видны только числами; изменённое имя пользователя нельзя найти по сводке. Принято: подробности добавляются отдельным изменением.
- Подтверждение применяет файл к конфигурации на момент нажатия, а не на момент выбора файла: если человек правил разрешения при открытом предпросмотре, итог считается от его правок. Предпросмотр при этом обновляется, расхождения нет.
