# Design

## Context

Домен уже вычисляет для пары действующие источники (`sources`) и неактивные разрешения (`inactive` с причиной `not-started`, `expired`, `revoked`). Экран показывает `sources` только при доступе и `inactive` только без доступа. Единого списка «все разрешения пары со статусом» нет. См. `proposal.md` (Why). Ограничения: расчёт доступа только в `src/domain/access.ts`, момент приходит параметром `at`, компоненты берут всё из `../app`, СБ: никаких записей и сети.

## Goals / Non-Goals

**Goals:**
- Один источник истины для состава и статусов разрешений пары, чтобы объяснение не могло разойтись с `granted`.
- Блок на экране с устойчивыми `data-testid` и `data-status`.

**Non-Goals:**
- Менять публичный результат `calculateAccess` и существующие списки `access-sources`, `access-inactive`.
- Показывать границы срока в числах отдельным полем, объяснять причины на уровне групп сотрудника.

## Decisions

### Где живёт логика

- Слой `src/domain`: чистая функция `explainAccess(config, query)` возвращает упорядоченный список `ExplainedPermission` (`kind`, `permissionId`, `groupId?`, `status: "active" | "pending" | "expired" | "revoked"`, `boundary?`). Статус считает существующая `inactivity` (она остаётся единственным местом правил интервала `[startsAt, expiresAt)` и отзыва). `calculateAccess` строит `sources` и `inactive` из результата `explainAccess`.
- Слой `src/app`: метод хука `explainAccess(userId, serviceId, moment)` переводит локальный момент в `Date` так же, как `checkAccess`, и реэкспортирует типы. Часы не читаются.
- Слой `src/components`: `App.tsx` только рисует строки и подбирает подписи; никакой даты и статусов не вычисляет.

### Связка с `calculateAccess`

`calculateAccess` не вычисляет статусы сам, а берёт их из `explainAccess`: `sources` это строки `active`, `inactive` остальные. Поэтому «доступ есть тогда и только тогда, когда есть строка `active`» выполняется по построению, а не по соглашению двух копий логики. Порядок прежний: прямые разрешения, затем групповые в порядке разрешений.

### Статус `revoked` и граница

Отзыв считается причиной, только если он раньше окончания срока (прежнее правило `revokedFirst`). Если отозвано позже окончания, на момент между ними статус `expired`, как и при расчёте доступа. Приоритет проверок прежний: `pending`, затем `revoked`, затем `expired`.

### Подписи

- Источник: «Прямое разрешение» или «Группа «<имя>»» (имя из конфигурации, при его отсутствии `id` группы), как в существующем `describeSource`.
- Статус: «действует», «ещё не началось, с <момент>», «истекло, закончилось <момент>», «отозвано <момент>». Моменты форматирует `formatMoment` в поясе браузера. Подпись истёкшего содержит и «истекло», и «закончилось»: тексты на экране прежнего расчёта говорят «закончилось», автопроверка Хекслета, вероятно, ищет «истекло». Точная формулировка проверяющего теста неизвестна; уточнить по первому прогону и поправить подпись, если потребуется.

### Альтернативы

- Собирать список в компоненте из `sources` и `inactive`: даёт два места правил порядка и риск расхождения; запрещено правилами слоёв.
- Новая функция расчёта рядом с `calculateAccess`: дублирует `inactivity`.

## Risks / Trade-offs

- [Расхождение подписей с проверяющим тестом] → подпись истёкшего содержит оба слова; проверить прогоном автопроверки и поправить.
- [Дублирование информации на экране: объяснение повторяет `access-sources` и `access-inactive`] → принято, существующие тесты и сценарии остаются; убрать дубли можно отдельным изменением.
- [Изменение `calculateAccess` задевает все сценарии доступа] → публичный результат не меняется; существующие тесты `access.test.ts` служат страховкой, добавляется проверка равенства `sources` строкам `active`.
