# Архитектурные правила

Приложение разложено на три каталога, и три правила держат эту раскладку. Независимое ревью сверяет дифф с этим документом, а автоматические проверки архитектуры привязаны к тем же каталогам.

## Каталоги

| Каталог | Что в нём лежит |
| --- | --- |
| `src/domain` | Модель данных (`model.ts`) и расчёт доступа (`access.ts`). Чистые функции без обращений к браузеру и без чтения часов. |
| `src/app` | Слой приложения. Хранилище браузера, формат файла конфигурации, операции над разрешениями и хук `useSimulator`, который отдаёт компонентам всё нужное. |
| `src/components` | Экраны на React и Mantine. Показывают данные и передают действия человека в слой приложения. |

## Правила

### Единый модуль расчёта для всех экранов

Доступ сотрудника к сервису считает один модуль, `src/domain/access.ts`. Каждый экран берёт результат из него и не пересчитывает доступ по-своему, иначе два экрана рано или поздно ответят по-разному. Срок действия разрешения уже считается в этом модуле: минута берётся из `at` по локальному часовому поясу, секунды отбрасываются; интервал полуоткрытый: начало включительно, окончание исключительно. Новая логика доступа, например объяснение источников, тоже добавляется в этот модуль.

### Момент расчёта передаётся в расчёт явно

Модуль расчёта не читает часы. В нём нет `Date.now()` и `new Date()` без аргументов, момент приходит параметром `at`. Слой приложения берёт текущее время и передаёт его вниз, а тест подставляет любой момент и получает повторяемый результат.

### Компоненты обращаются к конфигурации только через слой приложения

Компонент не читает `localStorage` и не импортирует модуль хранилища. Он получает конфигурацию и операции из `useSimulator` и результат расчёта из `checkAccess`. Компонент также не импортирует `src/domain`, расчёт ему отдаёт слой приложения.

## Где живут общие типы

Типы данных (`Config`, `User`, `Group`, `Service`, `Permission`, `Subject`) и типы результата расчёта (`AccessResult`, `AccessSource`, `InactivePermission`) объявлены в `src/domain`, потому что их смысл задаёт расчёт и модель. Слой приложения реэкспортирует их из `src/app/index.ts`. Компоненты импортируют из `../app` всё, включая типы, и исключения для `import type` из `src/domain` нет. Граница одна для значений и для типов, поэтому правило про импорты не приходится читать с оговорками.

Новый общий тип объявляется в `src/domain`, а если он нужен компонентам, реэкспортируется из `src/app/index.ts`. Типы, которые задаёт сам слой приложения, например результаты операций `GrantResult` и `ImportResult`, объявляются прямо в `src/app/index.ts`. Компоненты берут их оттуда же, через `../app`, как и остальные типы.

## Тесты

Тесты лежат рядом с кодом и называются `*.test.ts` и `*.test.tsx`. Правила импортов описывают код приложения. Тесты компонентов вправе брать из `src/app` учебные данные, ключ хранилища и функции формата файла, чтобы подготовить состояние браузера и сверить его после действия.

## Проверки

`make lint-arch` запускает ast-grep по `src` с правилами из каталога `rules`. Сейчас там лежит `rules/architecture.yml`, и он закрепляет проверками три правила выше и часть требований безопасности:

| Правило | Что запрещает |
| --- | --- |
| `domain-no-clock` | `Date.now()` и `new Date()` в `src/domain` |
| `components-no-local-storage` | `localStorage` и `sessionStorage` в компонентах |
| `components-no-domain-or-storage-import` | импорт `domain` и `storage` в компонентах, включая `import type` |
| `no-network-ts`, `no-network-tsx` | `fetch`, `XMLHttpRequest`, `WebSocket`, `navigator.sendBeacon` в `src` |

Тесты (`*.test.ts`, `*.test.tsx`) из проверок исключены. Каждое правило описано отдельно для `.ts` и `.tsx`, потому что ast-grep выбирает файлы по языку. Новые правила добавляются файлами `rules/*.yml` (см. скил `add-arch-rule`), а изменение правил отражается в этом разделе.
